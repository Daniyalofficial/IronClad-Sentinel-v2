# Disaster recovery and operations

## What is actually state

| Data | Location | Recoverable from |
|---|---|---|
| Organizations, users, sessions, tokens | database | backup |
| Projects, scans, findings, events | database | backup |
| Policies, baselines (server-side) | database | backup |
| SBOMs and components | database | backup |
| Integrations (incl. secrets) | database | backup |
| Audit log | database | backup |
| Queued/in-flight jobs | database | backup (reclaimable after the stale timeout) |
| Baseline files used by CI | the scanned repository (`.ironclad/baseline.json`) | git |
| Policy files used by CI | the scanned repository (`policy.yaml`) | git |
| Reports | derived | re-run a scan |

**Everything that matters is in the database.** Reports and SBOMs are
derived and can be regenerated by re-scanning.

## Backup

### PostgreSQL

```bash
# Custom-format dump: compressed, parallel-restorable, schema+data
pg_dump -Fc -Z6 ironclad > ironclad-$(date +%F).dump

# Or, for point-in-time recovery, run continuous WAL archiving:
#   archive_mode = on
#   archive_command = 'test ! -f /wal/%f && cp %p /wal/%f'
```

Recommended cadence: nightly full dump, retained 30 days, plus WAL
archiving if you need recovery to a point in time rather than to last
night.

### SQLite (single-host installs)

```bash
sqlite3 .ironclad/ironclad.db ".backup '/backups/ironclad-$(date +%F).db'"
```

Use the `.backup` command, not `cp` — copying a live database file can
capture a torn write.

### Configuration

The database URL and signing key live in your secret manager
(Kubernetes Secret, Vault, environment). Back those up separately:
without `IRONCLAD_SIGNING_KEY`, previously issued stateless tokens stop
validating.

## Restore

### Verify the backup first

```bash
pg_restore --list ironclad-2026-08-27.dump | head    # is it readable?
```

### Full restore into a fresh database

```bash
createdb ironclad_restored
pg_restore -d ironclad_restored --no-owner ironclad-2026-08-27.dump

# Confirm the schema version matches the code you are about to run:
IRONCLAD_DATABASE_URL=postgresql+psycopg2://user:pass@host/ironclad_restored \
  python -c "from ironclad.platform.database import build_engine, current_schema_version; \
print(current_schema_version(build_engine()))"
```

If the schema version is older than the code, run migrations:

```bash
IRONCLAD_DATABASE_URL=... python -c "from ironclad.platform.database import \
build_engine, run_migrations; print(run_migrations(build_engine(), verbose=True))"
```

### Restore drill

A backup you have never restored is a hypothesis. The restore path is
covered by `tests/test_database.py::test_schema_can_be_rebuilt_from_scratch_and_holds_data`,
which builds a fresh database from migrations alone and replays
representative rows — if the migrations and the models drift, that test
fails rather than your restore failing at 3 a.m.

## Failure modes and expected behaviour

| Failure | Behaviour | Recovery |
|---|---|---|
| Database unreachable | `/ready` returns 503; API requests fail; workers retry | Restore connectivity; queued jobs are still in the table |
| Worker killed mid-scan | The job stays `running` past the stale timeout and is reclaimed by another worker | Automatic |
| Scanner exception | The scan row is set to `failed` with the error recorded; the job retries up to `max_attempts` then goes `failed` | Inspect `GET /scan/{id}` and the worker log |
| Scan target deleted while queued | The scan fails with a `TargetError` rather than reporting "succeeded, 0 findings" | Re-queue after the target is back |
| Integration endpoint down | Delivery retried ≤3 times, then `last_status=failed` with the reason recorded | `POST /integrations/{id}/test` |
| Advisory feed unreachable | Falls back to the bundled database, warning recorded | Nothing to do |
| Duplicate scan request | `idempotency_key` returns the existing scan; no duplicate work | Automatic |
| Migration checksum mismatch | Startup fails with an explicit error naming the file | Add a new migration; do not edit history |

## Data retention

Nothing is deleted automatically. Retention is your decision:

```sql
-- Example: prune findings from scans older than a year.
DELETE FROM findings
 WHERE scan_id IN (SELECT id FROM scans WHERE created_at < now() - interval '365 days');
```

**Do not** apply a retention policy to `audit_events`. The audit log is the
record of who accepted which risk; pruning it defeats the purpose. If
regulation requires it, archive to immutable storage instead of deleting.

Archiving a project (`DELETE /projects/{id}`) sets `archived_at` and never
deletes history, for the same reason.

## RTO / RPO

| Deployment | RPO | RTO |
|---|---|---|
| SQLite single host | last `.backup` (you choose the cadence) | minutes: restore file, restart container |
| Postgres, nightly dumps | up to 24 h | 15–30 min: restore + migrate + smoke test |
| Postgres + WAL archiving | seconds to minutes | 15–30 min |

## Post-restore checklist

1. `curl -fsS /ready` returns `{"ready": true}`
2. `GET /version` reports the expected build
3. Sign in to `/ui/` as an owner
4. `GET /audit` shows historical entries (proves the audit table restored)
5. Queue one scan and confirm it reaches `succeeded`
6. `GET /metrics` shows `ironclad_queue_depth` values
